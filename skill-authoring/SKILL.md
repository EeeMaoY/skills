# 编写与修改 Skill

## 三条硬性规则

**1. 个人信息按仓库可见性区分对待。**
- **公开仓库：绝不出现**学号、姓名、邮箱、账号、真实主机名、内网地址、密钥凭证。需要身份就用占位符（`<学号>`、`<姓名>`、`<用户>`、`~`），并写明「以仓库中已有文件为准」。
- **私有仓库：允许包含**——仓库专属的具体值本就该写在项目级 skill 里，不必占位符化。

改 skill 前**先确认仓库可见性，不要凭印象**：

```bash
gh repo view --json visibility                                    # 装了 gh 时
curl -s -o /dev/null -w '%{http_code}\n' \
  https://api.github.com/repos/<owner>/<repo>                     # 404 = 私有；200 = 公开
```

（未认证探测只能识别公开仓库；404 也可能是仓库不存在。）私有仓库日后可能转为公开，放进去的个人信息届时即暴露，写入前想清楚。

**2. 动笔前先与远端对齐。**在哪个仓库改 skill，就先在那个仓库 `git fetch` 并检查是否落后于上游；落后就先 `git pull`（必要时 `--rebase`）。基于过期版本修改会造成冲突或覆盖他人更新。

**3. 通用与专属分开。**默认把**通用的部分提取到全局 skills 目录**（`~/.claude/skills/`），只把确有必要、与具体仓库绑定的部分留在该仓库的 `.claude/skills/` 下。除非用户明确要求某个 skill 只属于某仓库，否则按此拆分。

## 放在哪里

| 内容性质 | 位置 |
| --- | --- |
| 跨仓库复用：格式规范、通用流程、工具用法 | `~/.claude/skills/<name>/SKILL.md`（全局） |
| 与某仓库绑定：该项目的目录结构、构建命令、课程或业务约定 | `<仓库>/.claude/skills/<name>/SKILL.md` |
| 每次会话都需知道的短约定（几条，不是长篇） | 该仓库 `CLAUDE.md`，**不是 skill** |

拆分后，项目级 skill 开头写一句「通用规范见 `<全局 skill 名>`，先读它」，**不要复制通用内容过去**——重复的内容迟早会漂移成两份不一致的版本。

## 格式

```
<skill-name>/
├── SKILL.md       # 必需：YAML frontmatter(name, description) + 正文
├── references/    # 可选：按需加载的详细资料（长文档、schema、API 参考）
├── scripts/       # 可选：可执行脚本，反复重写同一段代码时收进来
└── assets/        # 可选：产出物要用的模板、图片、字体
```

只创建实际需要的子目录，不要为了「看起来完整」建空目录。

### description（决定 skill 何时被加载）

用**第三人称**，并写出**用户会实际说出的触发短语**。这是 skill 唯一常驻上下文的部分，值得反复打磨。

```yaml
# 好：第三人称 + 具体触发词
description: 撰写、编译或检查某类报告时使用。当用户要求「写报告」「编译报告」「检查报告能否提交」，或需确认命名/骨架约定时使用。

# 差：第二人称、含糊、没有触发词
description: Use this skill when working with reports.
description: 提供报告相关指导。
```

正文里的其他部分同样避免第二人称，改用祈使句、动词开头（「先确认…」「不要把…」而不是「你应该…」）。

### 正文

- 目标是**让另一个 Claude 实例能照着做**：写「怎么做」的程序性知识，不写「是什么」的背景介绍。
- 控制在 **1500–2000 词以内**；超出就把细节挪到 `references/`，在正文里指明何时去读。
- 用表格、清单、代码块代替长段落。
- 正文引用到的每个 `scripts/`、`references/`、`assets/` 文件都必须真实存在。

## 流程

1. **明确触发场景**：用户说什么话时该加载它？把这句话提炼进 description。
2. **规划复用资源**：把这个任务从头做一遍，哪些东西是会反复重写或反复查的？那些该进 `scripts/` 或 `references/`。
3. **判断归属**：按上文三条规则决定放全局还是项目级。
4. **写 SKILL.md**：先写 frontmatter，再写正文。
5. **自检**（见下）。
6. **提交与推送**：改完只做本地提交，或者先不提交，把改动报告给用户；**推送前必须先征得用户同意**。改完顺手就推是错的——推送是对外动作，推出去就收不回来。

## 自检清单

- [ ] frontmatter 有 `name` 与 `description`；description 为第三人称且含具体触发短语
- [ ] **公开仓库：全文（含文件名、示例、路径）无任何真实个人信息**——用 `grep` 搜学号、姓名、邮箱、用户名确认；**私有仓库允许包含**（但已确认过可见性）
- [ ] 通用内容已提取到全局，只有仓库相关内容留在项目级
- [ ] 项目级 skill 引用了全局 skill，而不是复制其内容
- [ ] 正文为祈使句，篇幅在 1500–2000 词以内，细节已移入 `references/`
- [ ] 引用的 `scripts/`、`references/`、`assets/` 文件均存在，脚本可执行
- [ ] 改之前已确认所在仓库与远端同步（`git fetch` / 必要时 `git pull`）
- [ ] **推送前已征得用户同意**（不要把「先与远端同步」误读成「改完就推」）
