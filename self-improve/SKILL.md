# 自我更新：沉淀偏好与迭代规则

把跨会话仍然有效的经验写进持久文件，让下一次会话直接受益。仅对当前任务有效的信息不落盘。

## 第一步：判断归属

| 信息 | 去处 |
| --- | --- |
| 仅对当前任务有效 | 不落盘 |
| 跨项目通用偏好（语言、验证习惯、git 约定等几条以内的短规则） | `~/.claude/CLAUDE.md` |
| 通用流程、可复用的做法 | 全局 `~/.claude/skills/<name>/SKILL.md`（新建或迭代） |
| 仅与某仓库绑定的约定 | 该仓库 `AGENTS.md` 或 `.claude/skills/<name>/SKILL.md` |

- 通用与专属分开：能提为全局的不留在单个仓库里。
- 在仓库中只写 `AGENTS.md` ，不创建 `CLAUDE.md` ，若原本已有也将其改成 `AGENTS.md`。
- 在写入仓库时，检查仓库所有性。若非用户本人所有的仓库，需要写明大概修改内容后，向用户二次确认。

## 第二步：写入前

1. **先读目标文件**，检索是否已有相同或相近内容：有则就地更新，绝不追加成重复条目——重复的规则迟早漂移成两份互相矛盾的版本。
2. **写「怎么做」而非「是什么」**：规则用祈使句；feedback 类经验要带上原因（为什么这样做）与执行方式（下次遇到什么情况就做什么）。
3. **检查目标仓库可见性**（用 `~` 代指家目录，不写真实用户名、主机名）：

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' \
     https://api.github.com/repos/<owner>/<repo>   # 200 = 公开
   ```

   公开仓库绝不写入个人信息；**密钥、凭证任何情况下都不写入**，私有仓库也不行。

4. **冲突或拿不准时先问用户**：新规则与已有内容矛盾、或信息归属不明时，不要自行取舍。

## 迭代 skill 本身

修改任何 `SKILL.md` 前，先加载 `skill-authoring` skill （若有） 并遵循其格式与自检清单（description 触发词、篇幅限制、references 拆分等），不要在这里重复那些规则。

## Git 兜底

目标文件受 git 管理时：

- 改前先与远端对齐（`git fetch`，落后则 `git pull`）。
- 按改动拆分 commit，一个 commit 一件事，commit message 写清改了什么、为什么。
- **推送前必须征得用户同意。**

## 生效时机

- `SKILL.md` 正文按需加载，改动后在当前会话再次触发即生效。
- frontmatter 的 `description` 与 `CLAUDE.md` 在会话启动时载入，改动通常要到下一次会话才生效——写入后告知用户这一点。
